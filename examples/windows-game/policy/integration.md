# Example: Lantern Trail integration and delivery

This fictional module belongs to the [example project](../PROJECT.md). The game
owner owns its requirements and action authority. Integration depends on VERIFY-01
through VERIFY-03 and EXEC-01/EXEC-02 for the affected work; no conflict is declared.

## INT-01

Requirement: agents may commit accepted source and integrate into local main
after applicable checks and separate final review. The owning item records actual
source/evidence, reviewer identity/findings and any unverified boundaries. Keep
recoverable source history. These fictional permissions do not authorize a real
repository action; a real project must record its own signature/review conventions.

## DELIVER-01

Requirement: an internal development candidate has an immutable source, exact
engine/toolchain and dependency/asset inputs, target and package digest. Its
maintained `game-package` command is fictional here. A clean Windows package
must start from an owned installation and complete the specified puzzle/input/save
smoke task without a developer checkout. State offline/runtime prerequisites.
Preserve existing saves and test incompatible/corrupt saves with synthetic copies.

## DELIVER-02

Requirement: public release/store upload, signing keys, credentials, spending and
external communication require a separate owner decision. A source merge or
successful development build does not authorize publication or store submission.
A project may implement its check map with local commands or a chosen CI provider;
no provider or runner is selected by this example. A new pipeline needs actual
positive, rejection, unavailable and artifact-identity checks before reliance.

## DELIVER-03

Requirement: retain the known-good package and save-format compatibility facts.
A failed smoke/install check stops publication. Restore the known-good owned test
installation only under recorded authority and rerun the smoke; retain the failed
candidate result. If older code cannot read migrated saves, stop for the approved
save-restoration or forward-repair procedure rather than overwrite saves. Product
release acceptance, later player feedback and source integration remain distinct.
