# Example: Lantern Trail execution

This fictional module belongs to the [example project](../PROJECT.md). The game
owner owns execution policy and must approve its real counterpart. Selection
and resource limits here describe a paper case; they authorize no actual tool.
No external module dependency or declared conflict applies.

## EXEC-01

Requirement: the fictional owner permits passive inspection of retained inert
source on its approved development workstation. This includes manifest/hash,
license/link and policy-reference checks with already approved offline tools.
Do not import/execute consumer modules, role instructions, hooks, document
examples, plugins, build steps or games through this boundary. Keep original
inputs unchanged, use owned outputs, and apply the check's documented file limits.
No source checker may read player saves or credentials by implication.

The standing maintenance boundary requires an accepted work item, semantic diff
review, exact inputs, separate review and INT-01 integration. Changes to tools,
permissions, gate selection, product behavior or unknown effects leave this
boundary and require their applicable route. It replaces no other requirement.

## EXEC-02

Requirement: synthetic gameplay/save/build checks run only in the fictional
owner's approved Windows development fixture with the recorded engine, no
production/player data and an owned test-save directory. Each task records CPU,
memory, disk, output, duration, attempts and cleanup bounds before execution.
A bound is a finite accepted value, not a blank field or unlimited default.
No network services, downloads, elevated rights, stores, credentials or tool
installation are authorized. Missing tools or executor authority stop that check.
The owner decides any new executor or effect; a passing host check cannot do so.

## EXEC-03

Requirement: failed/cancelled attempts retain source, outcome and cleanup evidence.
Classify failure before a permitted retry; no implicit renewed budget or use of
another worker follows. Temporary allowances name scope, approver, expiry/event
and alternatives in the owning work item and canonical decision. Active exceptions
are listed in PROJECT; expired history remains linked and grants no permission.
